# AGENTS.md: PTO AI, backend

## Продукт

Сервис проверки исполнительной документации для инженера ПТО. Пользователь загружает пакет цифровых документов (PDF с текстовым слоем, DOCX, XLSX/CSV), система извлекает данные, проверяет их правилами и отдаёт замечания, комплектность и PDF-отчёт.
OCR и сканы в текущий этап **не входят**: файл без текстового слоя получает статус `needs_ocr`.

## Стек

NestJS, TypeScript, Prisma, PostgreSQL, Redis, BullMQ, S3-совместимое хранилище (MinIO локально, Yandex Object Storage в проде), zod, Docker Compose, Jest.

## Команды

```bash
yarn
docker compose up -d          # postgres, redis, minio
yarn prisma migrate dev       # миграции
yarn start:dev                # API
yarn start:worker             # воркер очереди (отдельный процесс)
yarn lint && yarn typecheck && yarn test   # обязательно перед завершением задачи
```

## Структура

```
src/
  modules/        auth, objects, packages, documents, findings, checklist, reports
  pipeline/       этапы: extract, classify, parse, rules, explain, report
  rules/          Rule Engine: реестр и правила (чистые функции)
  llm/            LlmClient (интерфейс) и реализации провайдеров
  parsing/        DocumentParser (интерфейс) и реализации по форматам
  common/         ошибки, guards, интерсепторы, логирование
prisma/           schema.prisma, migrations
docs/             openapi.yaml, tasks.md
```

## Главные правила (нарушать нельзя)

1. **Контракт первым.** `docs/openapi.yaml` источник правды. Не менять эндпоинты, поля и статусы без прямого указания. Если для задачи нужна правка контракта, сначала предложи diff для `openapi.yaml` и жди подтверждения.
2. **Источник правды по статусам это PostgreSQL.** Redis только для очереди BullMQ, pub/sub прогресса и кэша. Потеря Redis не должна терять данные.
3. **Правила проверки детерминированные.** Rule Engine это чистые функции с юнит-тестами. LLM **не принимает решений** о нарушении: только извлекает поля и формулирует пояснения.
4. **У каждого извлечённого значения и замечания есть `SourceRef`** (файл, страница и bbox, либо лист и ячейка).
5. **Этапы пайплайна идемпотентны.** Результат каждого этапа сохраняется в БД, любой этап можно перезапустить отдельно. Повторный запуск не должен создавать дубликаты.
6. **Ошибка одного файла не роняет пакет.** Причина пишется в статус этапа документа, остальные продолжают обработку.
7. **Все вызовы LLM только через `LlmClient`.** Прямых вызовов SDK в бизнес-логике нет. Ответ LLM всегда валидируется zod-схемой. Результаты кэшируются по хэшу файла и версии промпта.
8. **Разбор файлов только через интерфейс `DocumentParser`.** Реализацию можно заменить (например, на внешний сервис).
9. **Версии.** Каждое замечание хранит `ruleId` и `ruleVersion`, каждое извлечение `promptVersion`.
10. **Безопасность.** Секреты только из переменных окружения, ничего не коммитить. Не логировать содержимое документов и персональные данные. Файлы отдавать только по временным ссылкам.
11. **База данных.** Изменения схемы только через миграции Prisma. Применённые миграции не редактировать.
12. **Формат ошибок** единый: `{ code, message, details? }`, тексты понятны человеку.

## Как работать

- Одна задача из `docs/tasks.md` за раз. Небольшой diff, не трогать несвязанные файлы.
- Не добавлять зависимости и новую инфраструктуру (Kafka, RabbitMQ и т.п.) без согласования.
- Если требование неясно, задай вопрос, а не угадывай.
- В конце кратко опиши, что изменено и как проверить.

## Ветки и коммиты (проверяют husky-хуки, не нарушай, чтобы не тратить попытки)

**Ветка** (`check-branch-name.cjs`, хуки pre-commit и pre-push):
- Формат `type/[ID-]описание` или `type/ID`. `type`: `feature | test | bug | fix` (строчными).
- ID задачи (`BEK-1`, `FRONT-7`: заглавные буквы 2-10 символов, дефис, число) необязателен. Описание: строчные латиница и цифры через дефис.
- Примеры: `feature/new-auth`, `feature/BEK-1`, `feature/BEK-1-repo-setup`, `fix/BEK-23-upload-timeout`. Служебные: `release/1.2.3`.
- Прямая работа в `main` и `develop` запрещена. Переименовать: `git branch -m <имя>`.

**Коммит** (`commitlint.config.cjs`, хук commit-msg): `[ID |] Тип | описание`
- `Тип` строго с большой буквы: `Feature`, `Test`, `Bug`, `Fix`. ID необязателен.
- Описание от 5 символов, без второго ` | ` внутри, заголовок до 120 символов, по-русски или по-английски.
- Примеры: `Feature | новый вариант авторизации`, `BEK-1 | Feature | создал репу с беком`.
- Не использовать `--no-verify`. Перед коммитом хук гоняет `lint-staged` и `typecheck`, перед пушем `lint`, `typecheck`, `build`.
